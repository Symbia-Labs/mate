# B9. The bot on a rented machine

B8 made the bot installable on a clean Linux machine. This increment puts it on one: a small Lightsail instance that runs the same single-game bot as the Mac, so that Symbia is available when the laptop is closed. Nothing about the bot changes. It is still lichess-bot with the Narrated engine class, one game at a time, with the config it has now. Replacing lichess-bot with a Rust connector, playing several games at once, and a health check are later increments.

## What it is

- **The machine.** Lightsail, Ubuntu 24.04, the 1 GB bundle with a public IPv4 address ($7 a month on the pricing page). The 0.5 GB bundle is $2 cheaper, but installing the Python environment on it may run out of memory, and I would rather not find that out on a machine I cannot log in to. The IPv6-only bundles are out, because github.com has no IPv6 address and the installer fetches lichess-bot from it.
- **How the package gets there.** A private S3 bucket holds the package. The instance is created with `deploy/firstboot.sh` as its launch script, which downloads the package through a signed link that expires, runs `install.sh`, and does not start the bot, because the token is not there yet.
- **How I see what happened.** I cannot log in to the machine. The launch script uploads its own log to the bucket through a second signed link when it ends, however it ends. After that, the only outside views are Lichess's public status and game export for Symbia, and the Lightsail API.
- **Ports.** The bot only makes outbound connections. Only SSH stays open, and only from Lightsail's own browser console.
- **The token.** It never passes through me. Brian pastes one command into the browser console. It asks for the token without echoing it, writes it to `/etc/symbia/bot.env` (mode 600, root only) and restarts the service.
- **Cutover.** Two copies on one token would both accept challenges, so the Mac bot is stopped first. It is idle between games, so one interrupt ends it cleanly.

## Predictions

Logged on the ledger before anything was created.

1. **It installs itself.** The report in the bucket shows, in order: the package unpacked and its checksums ok, the engine answering, lichess-bot at `f2b38b4f…`, the Python environment ready, the service enabled and not running, `systemd-analyze verify` clean on the real unit, and "first boot finished".
2. **Same answers on the real host.** Both fingerprint runs on the instance hash to `3227240a8328157d45c27b6206e0ad5b03c1eef1a1536c7a169373f08e67d9f9`, the Mac's.
3. **Speed.** The instance searches at 0.6 to 1.2 million nodes a second. The build workspace did 0.84 to 0.96 and the Mac 1.71. The second run is within 20% of the first, which would mean the shared processor does not throttle under two minutes of steady load.
4. **Nothing else is reachable.** Of the instance's ports only SSH is open, and only to Lightsail's console range.
5. **Cost.** The bundle is $7.00 a month by the API's own price, and the only other thing created is the bucket.
6. **Cutover.** With the Mac bot stopped first and the token pasted, Lichess shows Symbia online within a minute, and the service reports active.
7. **A game from the host.** Brian plays one game. Symbia moves without flagging, narrates both sides in the chat, and the game appears in Symbia's Lichess export with a normal ending.
8. **Reboot.** After the instance is rebooted through the API, Symbia is online again within five minutes with nobody touching it.

Predictions 1 to 5 are checked before the token exists. Predictions 6 to 8 need Brian.

## Not in this increment

Stopping the service in the middle of a game (whether lichess-bot finishes the game first has never been tried), a health check and the daily pull of Symbia's games, a challenge policy for strangers, measuring the bot's strength at the host's speed, and any change of connector or concurrency.

## Change at cutover: the token goes in from a terminal, not the console

Predictions p1 to p5 were scored on the first instance (see the ledger record `chess.b9.result`). For p6 the brief said Brian would paste the token into the Lightsail browser console. He declined to sign in to a browser, and this Mac has no AWS credentials, so the token has to travel from his terminal. The first instance could not take it that way: a launch script runs once, at first boot, and that one did not wait for anything.

The new route replaces the instance with one whose launch script (`deploy/firstboot.sh`) waits for the token:

1. `dist/handoff.sh`, filled in from `deploy/handoff.sh` at launch, reads the token in Brian's terminal without echo and sends it to a signed link that can only write one object in the private staging bucket.
2. The instance fetches that object, asks Lichess whether the token belongs to the Symbia bot account, writes it to `/etc/symbia/bot.env` (root only), starts the service and overwrites the object. Claude then deletes the object. The bucket is private, blocks public access, encrypts at rest and has no versioning, so deletion leaves no copy.
3. The token never passes through Claude, the ledger or the first-boot log (the log is scrubbed of anything shaped like a token before upload).

Two other changes: before waiting, the new script starts the service once with a token that cannot work and reads the journal, because the unit had never run on a real machine (a mistake there should show before the real token does); and it skips the two fingerprint runs, which were already scored on the first instance.

Tested before launch against stand-ins for curl, systemctl and journalctl: good token, token for another account, malformed token, and no token before the deadline. Each ended as intended, the root-only file was written only in the good case, and no token text reached the uploaded log.

p6 then reads: Brian runs one command in his terminal and pastes the token; Symbia shows online in Lichess's status and the service is active. p7 and p8 are unchanged.

What went wrong on the way: the first hand-off failed because the launch script used a bash-only test and Lightsail runs launch scripts under `sh`. The token was not used and its S3 copy was blanked; a second instance (`symbia-bot-2`) took the second hand-off. The local tests ran under bash, so they could not see it. They run under dash now.

What this does not show:

- Strength at this speed. The machine searches at 40% of the Mac's speed; the ~1870 estimate was measured on the Mac.
- That the narration read well. The sentences are not recoverable from the machine yet.
- That the service stops cleanly. The unit signals the whole service group, so SIGINT should reach the stream watcher, but no game was interrupted. B10.
- Anything about several users at once; the config is still one game at a time.

Left behind: the first instance `symbia-bot` is idle and costs money until it is deleted. The Mac bot is stopped and must not be started while the hosted one runs.
