# B10. Updating the hosted bot without rebuilding it

B9 put the bot on a rented machine, but the only way to change what runs there was to build a new machine and paste the token again. A launch script runs once, the machine has no outside address I can run commands on, and nothing on it looks for new files. Every change, such as a new greeting, a narration fix or a new engine, would cost a new instance, a new hand-off and about six minutes. This increment adds the missing path. It changes no chess and no bot behavior.

## The design: two halves

**Apply** lives on the machine and does not care how a package got there. `symbia-apply` takes a package, checks it, waits until no game is running, stops the bot, installs, starts the bot, and checks that the bot reached Lichess. If any of that fails it puts the old files back and marks the package as rejected, so it is not tried again.

**Transport** is how bytes reach the machine. The first transport is a push over SSH from the Mac:

1. Claude opens port 22 to the Mac's current address only (a /32 rule), for one push.
2. Claude asks Lightsail for a temporary SSH key and certificate for the instance. The certificate is valid for about 13 minutes (measured; the first draft of this document said 60 seconds) and the host's public keys come back with it, so the connection is checked against a key AWS vouches for, and no key has to be trusted on first sight. ssh pairs a certificate with its key only when the file is named after the key with `-cert.pub` on the end.
3. The Mac logs in once. In that one session it sends the current `symbia-apply`, installs it, hands it a signed link to the package and its checksum, and prints the result.
4. Claude closes port 22 again and deletes the temporary key objects.

Nothing is stored between pushes: no key on the Mac, no credential on the machine, no open port. The cost is that each push needs Claude, since Claude holds the AWS access that mints the key. That matches how the project is run, and a pull-based transport can be added later because apply does not depend on the transport.

Every push carries its own copy of `symbia-apply`, so a bad updater is replaced by the next push, which is the reason the updater is not left to update itself.

### Rules apply follows

- **Never interrupt a game.** The bot is stopped only when Lichess says no game is in progress (`/api/account/playing` with the bot's own token). If Lichess cannot be reached, the answer is "cannot tell", which is treated as busy. A busy package stays pending and a one-minute timer on the machine retries it.
- **Check before trusting.** The package's checksum must equal the one sent with it, every file inside must match its `SHA256SUMS`, the archive may only contain paths under `symbia-chess/`, and the installer's own checks (engine answers `uci`) run.
- **Keep the way back.** Before installing, the files it will replace are saved. A restart that does not reach Lichess within 90 seconds restores them, restarts, and reports that it rolled back.
- **Leave the token alone.** `/etc/symbia/bot.env` is read only to ask Lichess about games. The token and the signed link are never printed or logged. The link is passed on standard input, not on a command line.
- **Do not start what was stopped on purpose.** If the service was not running when the package arrived, it is installed but not started.

### What a package is now

`tools/package.sh` also writes a `RELEASE` file: the first 12 hex characters of the SHA-256 of `SHA256SUMS`. It names the package, so a config-only change gets a new name even though the engine binary is the same. `install.sh` stores `RELEASE` and `VERSION` under `/opt/symbia-chess`, and runs `symbia-apply setup` so that a freshly built machine has the updater from the start.

## Why SSH and not a bucket the machine pulls from

A Lightsail bucket can be attached to an instance so that the instance reads it with no key stored on it. It costs 1 USD a month, and putting files into it from outside takes a long-lived access key, which would pass through Claude and sit in the cloud. Push avoids that. The bucket route remains the way to get updates with nobody present, and is recorded as a gap, not built.

## What needs Brian's yes

Opening port 22, even to one address for a minute, changes the instance firewall. Each push starts only when Brian asks for it, and the closing step runs even if the push fails.

## Predictions

Logged on the ledger before anything was run.

Checked in the build workspace under dash (the shell Lightsail uses), against stand-ins for `systemctl`, `journalctl` and the Lichess call:

1. **The tests find a bug.** The first complete run of the suite has at least one failing case. (B9's script passed every bash test and still failed on the machine.)
2. **A busy bot is never touched.** In every case where Lichess reports a game or cannot be reached, the log of service commands has no stop, kill, start or restart, and the installed files are byte-identical afterward.
3. **Rollback is exact.** After a failed health check and after an installer that fails halfway, the installed tree hashes the same as before, the release is marked rejected, and the next run does not try it again.
4. **No secrets in the output.** Neither the test token nor the signed link's query string appears in the standard output, the apply log or the status file, in any case.
5. **Bad input changes nothing.** A wrong checksum, a file altered inside the package, and an archive with a `../` member each exit nonzero and leave the installed tree and the pending directory as they were.
6. **The push payload works as sent.** The script `deploy/push.sh` sends, run under sh in a sandbox, installs the updater and applies a package fetched from a file URL, with the same result as running apply directly.

Checked on `symbia-bot-2` (needs the firewall step):

7. **No rebuild, no paste.** One push replaces the bot files and restarts the service. The instance keeps its creation time, no token is pasted, and Lichess shows Symbia online within three minutes of the push starting.
8. **The login works on the first try.** The temporary certificate is still valid when the Mac connects, on the first attempt.
9. **The window is short.** Port 22 is open to the Mac's address for less than three minutes in total, and the rules read back as the console range only afterward.
10. **The idle check works with a real token.** `/api/account/playing` answers 200 with an empty list while the bot is idle.
11. **A clean stop.** Stopping the idle service takes under 20 seconds and the journal shows no kill.
12. **The introduction reaches a game.** In the next game the chat shows the new greeting and the two introduction lines. This needs Brian.

### What the live pushes found

All three defects were differences between the sandbox and the machine, and none could have been seen from inside the sandbox.

**A. Certificate name.** The certificate Lightsail issued was valid, and the key matched, but the login failed with "invalid format" and then "Permission denied (publickey)". ssh loads a user certificate only from `<key>-cert.pub`. `push.sh` now requires that name and ignores the user's own ssh configuration.

**B. Ownership.** After the first install, `.tools/lichess-bot` belongs to the `symbia` user. The installer, run as root by the updater, called git on it, and git refused ("detected dubious ownership"). The updater rolled back and the bot came back, which was the first live proof of rollback, but the update did not install. Every git call on that directory now names it as safe for that one call (`lbgit` in `install.sh`). The sandbox tests ran everything as one user and missed it. The container rehearsal now reproduces it by giving the directory to another user id first; before the fix it fails with the same message, and after the fix it installs.

**C. Rollback left files behind.** On a machine installed before the updater existed, there is no `RELEASE` or `VERSION` to put back, and `restore()` never removed the failed package's copies. The live machine reported the rejected release as installed after the rollback. `restore()` now removes both before restoring, and a new case (`install_fail_first`) starts from a tree without them; without the fix it fails three assertions.

The shared lesson is that the exact-tree assertion in prediction 3 was only as strong as the starting tree. Every test tree started with a `RELEASE`, so the one condition that matters on the first real update was never tested.

The idle spare instance `symbia-bot` was deleted at the end of this increment, at Brian's instruction. `symbia-bot-2` is the only instance.

## Not in this increment

A pull-based update with nobody present, signed packages (the checksum travels with the push, so whoever can log in as root already controls the machine), a standing health report, and strength at the host's speed. `install.sh` itself still has no test in the dash suite; it is covered only by the container rehearsal and the live push. What a push prints (status, recent journal) is the only view of the machine until a health report exists.
