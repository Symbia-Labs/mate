# B8. A bot that runs without the Mac

Everything the bot needs today sits on one laptop: a macOS binary, a config full of `/Users/briangilmore` paths, a start script that calls `caffeinate`, and an interactive prompt for the token. This increment makes the bot something that can be unpacked on a fresh Linux machine and started. It does not rent the machine; that is B9.

## What it is

- `tools/fingerprint.py`: asks the engine for a move in each of the 602 positions of the sample games (`tests/fixtures/games_sample.moves`, written from the PGN by `tools/games_moves.py`) at a fixed depth, with `Narrate` on, and writes one row per position: move, depth, score, nodes, principal variation and sentence. Clock fields are left out. It prints the SHA-256 of the rows. Two builds of the same source must print the same hash, and this is how "the same engine on a different machine" is checked: if the hashes agree, the search made the same choices in every position.
- A Linux build of the engine. The target is `x86_64-unknown-linux-musl`, which links statically and so does not depend on the glibc of whatever machine it lands on. If it turns out slower than the ordinary glibc build, the glibc build ships instead and the package says which Ubuntu it needs.
- `deploy/`: `install.sh` (unpack, fetch the pinned lichess-bot, make its Python environment, install the unit), `symbia-bot.service` (systemd: restart on a crash, stop with SIGINT so a running game finishes), and `lichess-bot.pin` (the exact upstream commit).
- `tools/package.sh`: builds `symbia-chess-B8-linux-x86_64.tar.gz` from a binary and the files above, with a `SHA256SUMS`.
- `bot/config.yml` and `tools/hook_smoke.py`: the config now uses paths relative to the lichess-bot directory (`../../target/release/` and `../../bot/games`), and the installed tree has the same shape as this repository (`target/release/uci`, `bot/`, `.tools/lichess-bot/`), so one config serves both. The smoke test now reads the real config instead of building its own with an absolute path, which hid exactly this kind of mistake.
- `bot/homemade.py`: the engine path is made absolute before the engine starts.

## What changed from the roadmap

The roadmap said a container image. This increment ships a tarball and a systemd unit instead, for three reasons. Docker is not running on the Mac and there is no daemon in the build workspace, so an image could not be tested here. Lightsail can run a script when the machine first starts, which can unpack a tarball but would need a registry to pull an image. And systemd already does the two things the container would have done for one process: restart on a crash and send a chosen signal on stop. A container can be added later without changing anything in this increment.

## Predictions

Logged on the ledger before any check ran.

1. The same answers on a different machine. The fingerprint of the Linux x86_64 musl build (Rust 1.97) is identical to the fingerprint of the Mac build (arm64, Rust 1.91.1), over all 602 positions at depth 5: same move, score, node count, variation and sentence. I expect this because the default graph computes with `f32` addition, multiplication, `min` and `max` only; the functions whose last digit differs between math libraries (`exp`, `ln`, `tanh`, `sin`) are used only by graphs that call them. If it breaks, the likely cause is a place I missed that does call one.
2. The glibc build agrees too: the same hash as the Mac.
3. The comparison can fail. Two runs of the Mac build give the same hash, so the fingerprint is stable. The same Linux binary run with `sharp=0` gives a different hash, so the fingerprint notices a change.
4. The static build is not much slower. Over the same 602 positions, the musl build searches at no less than 85% of the speed of the glibc build, single thread. About 65% sure: the loose-piece code allocates a vector per evaluation, and musl's allocator is slower than glibc's. If this fails, the glibc build ships.
5. The pin is what has been running. Every file in upstream lichess-bot commit `f2b38b4f3ec4fc990001c05a4000fcf8adbb339d` is byte-identical to the copy in `.tools/lichess-bot` on the Mac, except `homemade.py` (ours replaces it) and files that were generated or added here.
6. A clean install works. On an empty directory on Ubuntu 24.04, with no Mac path anywhere, unpacking the package and running `install.sh` ends with: the installed engine's fingerprint equal to the Mac's; `hook_smoke.py`, run from the installed tree with the unchanged `bot/config.yml`, passing (the class loads, the engine starts, a sentence reaches the mock chat); no occurrence of `/Users/` in the package or the installed tree outside the Python environment; no token in either; a package under 2 MB.
7. The relative paths work on the Mac too: `hook_smoke.py` with the unchanged `bot/config.yml` passes there.
8. The unit is well formed: `systemd-analyze verify` on the installed unit prints nothing.

Predictions 1 to 3 and 5 to 8 are checked by the scripts named in them. They say nothing about a live game or about how the bot behaves when systemd stops it; both belong to B9.

## Not in this increment

Renting the machine, putting the token on it, a real game from it, stopping the Mac's copy, the health check, the daily pull of the games, and the challenge policy. Also not here: hardening options in the unit (they are easier to add once the service runs on the real machine than to guess without it) and a container image.

## Results

All eight predictions held. The Linux checks ran on an Ubuntu 24.04 machine with two virtual CPUs, the same operating system Lightsail offers.

| # | Prediction | Result |
|---|---|---|
| 1 | The static Linux build gives the Mac's fingerprint | Held. Both hash to `3227240a8328157d45c27b6206e0ad5b03c1eef1a1536c7a169373f08e67d9f9`: 602 positions, 106,989,330 nodes each, same move, score, variation and sentence in every row. Mac: arm64, Rust 1.91.1. Linux: x86_64, Rust 1.97. |
| 2 | The ordinary (glibc) build agrees too | Held. Same hash. |

| 4 | The static build is at least 85% as fast | Held, narrowly. Static: 0.85 and 0.88 Mnps. Ordinary: 0.96 and 0.95 Mnps, alternating runs. The static build ran at 91% of the ordinary one (89% and 93% in the two pairs). The static build ships. |
| 5 | The pin is what has been running | Held. Of the 67 files in commit `f2b38b4f…`, 66 are byte-identical to the copy on the Mac. The one that differs is `homemade.py`, which ours replaces. The Mac copy also holds two generated log files. |
| 6 | A clean install works | Held. On an empty directory, `install.sh` unpacked the package, fetched lichess-bot at the pinned commit and built its Python environment. The installed engine hashed to the same fingerprint as the Mac. `hook_smoke.py` from the installed tree, with the unchanged config, posted six sentences to the mock chat. No `/Users/` string appears in the package, the installed tree or the engine binary. The only token in either is the placeholder. The package is 1,645,815 bytes. |
| 7 | Relative paths work on the Mac | Held. `hook_smoke.py` with the unchanged `bot/config.yml` posted eight sentences. |
| 8 | The unit is well formed | Held. `systemd-analyze verify` printed nothing. |

Three controls were run that were not predictions. A package with one byte changed is refused by the installer, and nothing is installed. A second install over the first succeeds. And `systemd-analyze verify` does flag a unit with a bad signal name and a bad restart setting, so its silence on the real unit means something (it exits 0 either way, so the test is that it prints nothing).

The installer's service branch (creating the `symbia` user, handing it the bot's folders, writing the token file with mode 600, writing the unit) was run once as root up to the `systemctl` call. It did all of that correctly and then stopped, because no systemd runs in this workspace.

## What this does not show

- That systemd starts the service, restarts it after a crash, or stops it the way the unit says. `systemctl` never ran. That is the first thing B9 does on the real machine.
- Anything with a real token: a connection to Lichess, a game from the host, or what lichess-bot does when it gets SIGINT in the middle of a game.
- That the bot plays as well on the host as on the Mac. This build machine searched at 0.95 million nodes a second against the Mac's 1.71 million. The bot manages its own clock, so a slower machine reaches less depth in the same time and plays weaker; the rating of about 1870 was measured at the Mac's speed. Lightsail's processors are shared and burstable, so B9 measures the speed on the plan it rents and re-rates if it is more than about 20% below the Mac.
- A reproducible Python environment. lichess-bot's `requirements.txt` gives ranges, not versions, so two installs on different days can differ. The install writes what it got to `bot/requirements.installed.txt`.

## What the package is

`tools/package.sh` builds `symbia-chess-<engine hash>-linux-x86_64.tar.gz` from a Linux build of `uci`. It refuses to build if a file names a Mac path or holds something that looks like a token. The engine is the static build (6.6 MB with debugging information; the package compresses to 1.6 MB). The ordinary build is 10% faster and needs glibc 2.34 or newer (Ubuntu 22.04, Debian 12), which the installer's first step, running the engine, would report at once on an older system. B9 can switch to it after measuring on the real machine.

## A defect found after the results, and fixed

`tools/hook_smoke.py` ended with `os._exit(0)`, which skips multiprocessing's clean-up, so every run left lichess-bot's helper processes (seven Python processes and the engine) running. It did this on every run since B6, including the one on the Mac today, which left one engine process alive; that process was killed by its exact ID, and the live bot, idle since 09:49, was not touched. The script now stops its child processes before it exits. In the Linux workspace a run now leaves nothing behind. The package built above contains the old script, so the package is rebuilt in B9 before it ships.

Measured while that was fixed: one mock game, the process tree of lichess-bot at `concurrency: 1`, takes about 81 MB of memory (proportional set size) in nine Python processes, and the engine takes under 1 MB, because it keeps no transposition table.
